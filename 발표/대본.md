## 1. 소개 (21초)

안녕하세요, 10조입니다. 저희 웹서버는 정적 파일을 직접 응답하고, 백엔드 서버로 요청을 중계하는 리버스 프록시 역할도 합니다. 오늘 발표할 설계는 하나, 요청을 처리하는 프로세스를 한 개만 둔 이유입니다.

## 2. 전체 구조 (24초)

저희 웹서버의 구조는 감독 프로세스 한 개와 워커 프로세스 한 개입니다. 워커 안에는 연결을 받는 메인 스레드 한 개와, 요청을 처리하는 루프 스레드 여덟 개가 있습니다. 감독 프로세스는 워커를 띄우고 지켜보며, 요청은 워커가 전부 처리합니다.

## 3. 왜 워커를 한 개로 했나 (39초)

워커 프로세스를 한 개로 둔 이유입니다. 업계에서는 워커를 여러 개 두는 방식을 많이 씁니다. 하나가 죽어도 나머지 워커의 연결은 그대로 유지되기 때문입니다. 하지만 저희는 루프 스레드가 이미 코어를 나눠 쓰니, 프로세스를 늘려도 처리량은 얻을 게 없다고 봤습니다. 얻는 것은 장애 격리 하나뿐인데, 캐시와 동시 요청 수 관리가 복잡해집니다. 이 비교는 잰 것이 아니라 설계 판단입니다.

## 4. 한 개로 충분한가: 다른 구현과 비교 (21초)

한 개로 충분한지 같은 조건에서 비교했습니다. 접속 100개를 동시에 열어 작은 파일을 계속 요청하니, 이 서버는 1초에 약 8만 6천 건이었고, 팀의 다른 구현 셋은 2만 6천에서 3만 3천 건이었습니다.

## 5. 워커 안: 누가 무슨 일을 하나 (34초)

워커 안의 역할 분담입니다. 로드밸런서와 프록시는 따로 띄운 프로그램이 아니라 스레드가 나눠 맡습니다. 메인 스레드는 새 연결을 연결 수가 가장 적은 루프 스레드에 넘기고, 백엔드가 살아 있는지 확인합니다. 루프 스레드는 그 연결을 끝까지 맡아 요청을 백엔드에 전달하고, 살아 있는 백엔드 중 처리 중인 요청이 가장 적은 곳을 고릅니다.

## 6. 백엔드 고르기 시험 (27초)

백엔드를 고르는 방식을 비교했습니다. 접속 16개로, 백엔드 하나가 0.2초씩 느린 상황에서 재 봤습니다. 번갈아 보내는 방식은 1초에 155건, 평균 103밀리초였고, 처리 중인 요청이 가장 적은 곳을 고르는 방식은 1초에 약 1만 6천 건, 평균 1밀리초였습니다.

## 7. 한 개의 대가와 감독 프로세스 (39초)

한 개의 대가는 워커가 죽거나 멈추면 서비스 전체가 멈춘다는 점이고, 감독 프로세스가 이것을 메웁니다. 요청을 보내는 중에 워커를 죽이니 약 11만 건 중 실패는 4건에서 6건, 죽는 순간 처리 중이던 요청뿐이었고, 0.11초 뒤 새 워커가 응답했습니다. 워커를 얼리면 11초 멈췄지만 그사이 요청은 실패 없이 늦게 처리됐습니다. 감독 프로세스 없이 죽이면 서버는 돌아오지 않았습니다.

## 8. 한계와 마무리 (15초)

남은 한계입니다. 죽는 순간 처리 중이던 요청은 잃습니다. 정리하면, 워커를 한 개로 해서 구조를 단순하게 지켰고, 그 대가는 감독 프로세스로 메웠습니다. 감사합니다.

## 질문 대비 (그림과 README에서 뺀 자세한 내용)

**최소 연결 비교 시험은 어떻게 했나** (2026-11-26, 같은 컴퓨터 macOS, 현재 코드 `build/webserver`)
- 백엔드는 파이썬 서버 2대(연결 유지). 하나는 즉시 응답, 하나는 요청마다 0.2초 지연. 이 서버가 `pool api <정책> max=256`로 두 대에 프록시. 직접 만든 클라이언트의 스레드 16개가 연결을 유지한 채 10초 동안 계속 요청. 정책을 번갈아 3번씩.
- round_robin: 초당 155~156건, 평균 103ms, p99 209~212ms, 느린 쪽이 받은 몫 50.0%. least_conn: 초당 15,476~16,801건, 평균 0.9~1.0ms, p99 1.6~1.8ms, 느린 쪽 0.2%. 실패 0.
- 한계: 한쪽이 극단적으로 느린 경우만 쟀고, 두 백엔드가 비슷할 때는 재지 않았다. 백엔드가 파이썬이라 절대값은 의미가 없다. 첫 시도는 연결 폭주로 실패가 많아 버렸고(클라이언트·백엔드 설정 문제), 연결 유지로 고쳐서 다시 쟀다.
- 설계 패치 문서에는 "least_conn을 round_robin으로 줄일지"가 아직 논의 전으로 남아 있다.

**워커 장애 시험은 어떻게 했나** (2026-11-26, 같은 컴퓨터 macOS, 현재 코드 `build/webserver`, 감독 프로세스 `-s`, 정적 파일 `index.html`(830바이트))
- 부하 도구: 직접 만든 파이썬 클라이언트. 스레드 16개가 요청마다 새 연결을 맺고 파일 1개를 받고 끊는다. 2초 뒤에 워커 프로세스에 신호를 보낸다. 요청 하나의 제한 시간은 25초. 시험 스크립트는 세션 임시 폴더에만 있고 저장소에는 없다.
- A, 워커 `kill -9`(10초씩 3회): 11만 건 안팎 중 실패 6, 4, 6건. 실패 종류는 연결 끊김(`ConnectionReset`)이나 빈 응답으로, 모두 죽는 순간 처리 중이던 요청이다. 죽은 뒤 첫 성공 응답까지 0.110, 0.108, 0.108초(이전 측정 109ms와 같다).
- B, 워커 `kill -STOP`(40초 1회): 33만 건 중 실패 4건. 이 4건은 얼리는 순간 처리 중이던 연결로, 제한 시간 25초가 지나도록 응답이 없었다(얼린 워커가 쥐고 있다가 교체 뒤 강제 종료될 때까지). 새로 들어온 요청 12건은 연결된 채 기다렸다가 11.0초 뒤에 모두 성공했다. 새 워커는 10번 연속 소식 없음으로 교체됐고 옛 워커는 강제 종료됐다(서버 기록).
- C, 감독 없이 서버 `kill -9`(6초 1회): 죽은 직후부터 끝까지 연결 거절(96,581건)이고 서버 프로세스는 돌아오지 않았다.
- 한계: 부하가 같은 컴퓨터의 CPU를 나눠 썼고 파이썬 클라이언트라 처리량 시험이 아니다. B는 1회만 했다. "워커 여러 개"는 만든 적이 없어서 캐시·동시 상한이 나뉜다는 것은 설계 판단이지 측정이 아니다. 감독 프로세스는 `-s`로 실행해야 켜진다.

**비교 테스트는 어떻게 했나** (2026-11-25, 같은 컴퓨터 macOS)
- 같은 1KB 파일, `ab -k -n 10000`. 처리량은 동시 100으로 3번 재서 중앙값: 이 서버 85,736 / 이전 구현 32,879 / 팀 구현 A 33,291 / 팀 구현 B 25,531 req/s (2.6~3.4배).
- 느린 연결: `GET / HT`까지만 보낸 연결 300개를 열어 둔 채 정상 요청 1개. 이 서버 0.59ms, 구현 B 0.62ms, 이전 구현과 구현 A는 5초 안에 응답 없음.
- 동시 1000 완주: 서버를 따로 띄우고 `ab` 10회, 1.5초 간격. 이 서버 10/10, 이전 구현 10/10, 구현 A 3/10, 구현 B 0/10. 이 서버도 다른 시험 직후 연속으로 잴 때는 3회 중 1회 끊긴 적이 있다. 끊기는 원인은 확인하지 못했다(macOS 대기열 한도 128과 관련 가능성).
- 이전 구현은 팀의 스레드 풀 구현(스레드 8개, 큐 1024). 구현 A는 다른 스레드 풀, 구현 B는 단일 스레드 이벤트 루프다.

**엣지 케이스 시험은 어떻게 했나** (2026-11-25, macOS, 현재 코드 `build/webserver`)
- 소켓으로 직접 만든 요청을 보내 응답 코드와 시간을 쟀다. 시간 제한은 시험하려고 짧게 줬다(머리 2초, 응답 1초). 기본값은 머리 10초, 응답 30초다. 본문 상한도 `max_body 1k`로 줬다.
- 결과: 끝나지 않은 헤더 408(2.0초), 메서드 FOO 501, 버전 2.5 505, 주소 20,000바이트 414, 헤더 20,000바이트 431, CL+TE 충돌 400, 서로 다른 CL 2개 400, `/../`·`%2e%2e` 400, 숨김 파일·심볼릭 링크 403, 본문 2,000바이트 413(상한 1k), 모두 1ms 미만.
- 백엔드: 무응답 504(1.005초), 연결 거절만 있으면 502(1ms), 죽은 곳+산 곳 20/20 성공.
- 끊김·복구: 요청 절반 보내고 끊은 연결 500개 → 열린 fd 536 → 36(전부 회수), 4번 반복해도 메모리 10.0MB로 안 늘어남(처음 2.0MB, 연결 500개분 버퍼가 힙에 남는 값). 워커 `kill -9` 109ms, `kill -STOP` 11.0초(연속 10번 확인 후 교체), 설정 다시 읽기는 새 연결 30만 건 × 3회 실패 0.
- **한계**: keep-alive 연결을 쓰는 `ab -k`로 부하를 주면서 설정을 다시 읽으면 `ab`가 3번 모두 중간에 멈췄다(10~14만 건 뒤). 교체 때 이미 맺어 둔 keep-alive 연결이 끊기기 때문으로 보이며, 이 원인은 코드로 확인하지 않았다(미검증). 클라이언트가 다시 연결하면 된다.
- 본문 상한을 넘으면 413은 오늘 직접 확인했지만 자동화된 기능 테스트는 없다.

**자동화된 테스트는 얼마나 되나**
- `make test`(2026-11-25): 단위 2,678개 검사 실패 0, 기능 100개(22묶음) 통과. 메모리·스레드 검사(ASan·UBSan·TSan 보고 0), 누수, 고장 주입(22개 중 21개, 1개는 sanitizer 빌드에서 구조상 실패)은 `README.md` 6장의 2026-11-24 값이고 오늘 다시 돌리지 않았다.

**req/s가 뭔가**
- 1초 동안 끝까지 처리해 응답한 HTTP 요청 수다. 부하 도구 `ab`가 동시에 N개 연결로 1KB 정적 파일을 계속 요청해서 쟀다. 높을수록 같은 시간에 더 많은 사용자를 받는다.

**워커, 루프 스레드, 이벤트 루프가 뭐가 다른가**
- 워커 프로세스 1개 안에 메인 스레드 1개와 루프 스레드 N개(코어 수, 이 맥은 8개)가 있다. 루프 스레드는 이벤트 루프(준비된 연결만 골라 조금씩 처리하는 반복)를 돌리는 스레드다. 메인 스레드는 연결 받기·헬스 체크·심장 박동만 하고 요청은 처리하지 않는다.
- Envoy·memcached에서 "워커"라고 부르는 것은 프로세스가 아니라 스레드이고, 이 서버의 루프 스레드에 해당한다. 이 서버의 "워커"는 프로세스(감독 프로세스가 띄우는 것)라서 이름이 겹친다.

**침묵 연결을 그냥 들고 있는 건가**
- 맞다. 연결 하나(수백 바이트)를 들고 있지만 스레드를 붙잡지 않는다. 루프는 커널(kqueue/epoll)에 "읽을 수 있게 되면 알려 달라"고 맡기고 `ev_wait` 한 곳에서만 잠든다. 침묵 연결은 알림이 안 오므로 CPU도 안 쓴다. 10초(기본값) 안에 아무것도 안 보내면 서버가 먼저 끊는다.
- 이전 구현 9.7초는 워커가 침묵 연결에서 읽기를 기다리다 제한 시간(약 10초)이 지나야 풀렸기 때문이다.

**처리량이 왜 유지되나 / 연결이 많으면 어떻게 되나**
- 루프 스레드 수가 코어 수로 고정이라 연결이 늘어도 일꾼이 늘지 않고, 서버 CPU는 이미 꽉 차 있다(macOS: 800% 중 468~515%, 병목은 서버 쪽 커널, `README.md` 6장). 그래서 약 10만에서 평평하다. 이전 구현은 워커가 8개뿐이라 동시 연결이 8개를 넘으면 나머지는 기다린다(동시 4: 56,299 → 16: 33,583). 왜 그만큼 떨어지는지 세부 원인은 따로 재지 않았다.
- 연결 상한은 `max_connections` 기본 4,096개이고 루프당 512개(4,096 ÷ 8)다. 시험(동시 500)은 상한에 닿지 않았다.
- 상한을 넘으면: 쉬는 연결 → 아무것도 안 보낸 연결 → 머리를 보내다 만 연결 순으로 내보내 자리를 만들고(`evict_one`, `conn.c`), 그래도 없으면 `503`과 `Retry-After: 1`로 돌려보낸다. 아직 받기 전의 연결은 커널 대기열(`listen` 1024, macOS는 시스템 한도 128)에서 기다리고, 메인 스레드가 한 번에 64개씩 꺼낸다.

**메인 스레드가 로드밸런서 역할도 하나**
- 맞다. 로드밸런서 역할이 둘이다. ① 메인 스레드가 새 연결을 연결 수가 가장 적은 루프 스레드에 나눠 준다(`pick_loop`, `src/main.c`, 동점이면 돌아가며). ② 루프 스레드가 요청을 처리 중인 요청이 가장 적은 백엔드에 보낸다(`pool_pick`, `least_conn`, `src/balance.c`). 둘 다 별도 스레드·프로세스가 아니라 호출하는 함수 하나다.
- 메인 스레드는 이 밖에 백엔드가 살아 있는지 2초마다 확인하는 헬스 체크도 한다. 헬스 체크가 바꾼 백엔드 상태(제외·복귀)를 루프 스레드들이 `pool_pick`에서 읽는다.

**워커를 여러 개로 하면**
- 기록(`설계-패치내역서.md` 패치 2): 워커 여러 개는 검토하고 버렸다. 죽어도 일부만 잃지만 캐시와 백엔드 동시 상한이 워커마다 나뉘기 때문이다. 하면 메인 스레드도 워커마다 생기고, 헬스 체크·심장 박동·캐시도 워커마다 따로 돈다.

**p99가 뭔가**
- 요청 100개 중 99개가 이 시간 안에 끝났다는 뜻이다. 가장 느린 1%를 뺀 최대 지연이라 "대부분의 손님이 겪는 최악"을 보여 준다.

**숫자는 어떤 조건인가**
- 같은 컴퓨터(macOS), 1KB 정적 파일, `ab` keep-alive, 커밋 `15f3bfa`, 2026-11-24 (`README.md` 6장).
- 침묵 연결 지연은 이 서버가 4개에서 0.28ms, 1,000개에서 0.25ms, 4,596개를 열었을 때 0.29ms. 스레드 풀은 8개에서 9,700ms, 72개에서는 40초 안에 응답이 없었다. 1만 개까지는 재지 않았다.
- **4,596개는 "들고 있는 수"가 아니라 "연 수"다.** 연결 상한이 4,096개라 클라이언트가 4,596개를 열어도 서버는 4,096개만 들고 있고, 초과분 500개는 서버가 가장 오래된 침묵 연결부터 먼저 끊는다(`evict_one`). 직접 확인: 4,596개를 열자 클라이언트 쪽에서 살아 있는 연결 4,096개, 서버의 ESTABLISHED 4,095개, 정상 요청 30/30 200 OK, 중앙값 0.26ms, 서버 메모리 +1.6MB(macOS, 루프 8개).
- 이전 구현은 큐가 기본값 64면 동시 200부터 연결이 끊겨 1024로 늘려 쟀다. keep-alive가 없으면 차이가 작다(동시 200: 39,824 대 35,856).
- 프록시 약 45,000 req/s(동시 64): 이 서버의 정적 모드를 가벼운 백엔드 2대로 두고 직접 잼(2026-11-25, `ab -k` 5만 건 2회 평균 45,349). 같은 조건에서 파이썬 백엔드 2대는 약 25,700, 가벼운 백엔드 1대에 직접 요청하면 약 62,800, 이 서버의 정적 파일은 약 96,900.
- 한계: `ab`·프록시·백엔드가 한 컴퓨터의 CPU를 나눠 썼고, "가벼운 백엔드"는 실제 앱 백엔드보다 가볍다. 따로 두고 재면 더 오를 수 있으나 재지 않았다(미검증).
- 캐시에 있는 응답은 두 번 재서 130,000과 183,500 req/s(편차 큼).

**락이 완전히 없나**
- 연결·요청 처리 경로에만 없다. 공유하는 것은 백엔드 상태·통계(atomic), 캐시(16조각 락), 설정(읽기 전용)이다.

**감수하는 것의 코드 근거**
- 한 번 배정: `pick_loop` (`src/main.c:49`), 연결 수가 가장 적은 루프에 한 번만.
- 백엔드 쉬는 연결은 루프·백엔드마다 16개까지만 보관: `IDLE_MAX` (`src/upconn.c`).
- 루프가 한 바퀴에 오래 걸린 시간: `max_busy_us` (`include/loop.h`), 상태 페이지에 표시.

**백엔드는 언제 제외·복귀하나** (`balance.c`, `health.c`)
- 연결 거절은 바로, 헬스 체크(2초마다)는 연속 3번 실패하면 제외. 연결 시간 초과 3번, 502·503·응답 전 끊김 5번도 제외. 복귀는 확인 2번 연속 성공.
- 다시 보내는 규칙: 한 바이트도 안 보냈으면 어떤 메서드든 다른 백엔드로, 보낸 뒤에는 본문 없는 GET·HEAD만 한 번. POST는 처리됐는지 모르므로 다시 보내지 않는다.

**워커가 멈춘 것은 어떻게 아나**
- 루프가 연결을 하나 진행할 때마다 센 값을 메인이 1초마다 보고, 10번 연속 안 늘면 새 워커로 교체. 시간이 아니라 "확인했는데 소식 없던 횟수"라서 노트북이 잠들었다 깨도 오판하지 않는다. 죽으면 0.1초 뒤 다시 띄우고, 거듭 죽으면 두 배씩 최대 30초.
